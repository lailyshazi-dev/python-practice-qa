# День 32: разбиение API-тестов по темам

## Что я сделал

- Создал ветку `refactor/split-api-tests-by-topic`.
- Разделил один большой файл `test_api_posts.py` на несколько файлов по смыслу.
- Создал файлы:
  - `test_api_get_posts.py`
  - `test_api_create_post.py`
  - `test_api_update_post.py`
  - `test_api_delete_post.py`
- Перенес тесты по соответствующим темам.
- Удалил старый общий файл `test_api_posts.py`.
- Запустил только API-тесты.
- Запустил все тесты проекта.

## Что понял

- Это рефакторинг: поведение тестов не изменилось, но структура стала лучше.
- Один большой файл становится неудобным, когда в нем появляются разные смысловые группы.
- Разделение по темам упрощает чтение, поиск и поддержку тестов.
- В маленьком проекте иногда нормально сначала сделать один файл, если тестов мало и задача срочная.
- Когда проект растет, структуру нужно улучшать вовремя, пока один файл не стал слишком тяжелым.

## Где это нужно в реальной работе

- В проекте с API постов один QA может работать над чтением данных, другой над созданием, третий над обновлением и удалением.
- Если все тесты лежат в одном большом файле, людям сложнее искать нужные проверки и они чаще мешают друг другу в Git.
- Если тесты разделены по темам, проще понять, где лежат проверки `GET`, где `POST`, где `PUT/PATCH`, а где `DELETE`.
- При срочной задаче команда может сначала быстро добавить несколько тестов в один файл, а потом, когда видно рост блока, провести рефакторинг и разложить их по структуре.

## Новые слова

- `refactor` - улучшить структуру без изменения поведения.
- `structure` - структура проекта.
- `by topic` - по смысловым темам.
- `maintainability` - удобство поддержки.
- `grow` - разрастаться.

## Правило дня

Не обязательно дробить код с первой минуты, но как только в одном файле появляются разные большие смысловые блоки, их стоит разделить.
