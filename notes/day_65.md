# День 65: Page Object Model в Playwright

## Цель урока

Вынести локаторы и действия со страницей из тестов в отдельный Page Object, чтобы тесты описывали пользовательские сценарии, а не технические детали интерфейса.

## Что сделано

- Создан пакет `tests/ui/pages`.
- Создан класс `TodoPage` в `tests/ui/pages/todo_page.py`.
- В `TodoPage` собраны локаторы TodoMVC:
  - поле добавления задачи;
  - список задач;
  - checkbox выполнения задачи.
- В класс добавлены действия и методы поиска:
  - `add_todo(title)`;
  - `complete_todo()`;
  - `todo_title(title)`;
  - `items_left(count)`.
- Fixture `todo_page` теперь открывает `base_url` и возвращает `TodoPage`.
- Тесты используют понятные методы страницы вместо повторения локаторов и действий.

## Что такое Page Object Model

Page Object Model, или POM, это подход, при котором отдельный класс представляет страницу или важный компонент приложения. Внутри класса хранятся локаторы и действия пользователя. Тест вызывает методы высокого уровня и проверяет результат.

```python
todo_page.add_todo("Learn Playwright locators")
expect(todo_page.items_left(1)).to_be_visible()
```

Тест читается как сценарий: пользователь добавил задачу, после этого осталось одно невыполненное задание.

## Почему локаторы находятся в Page Object

Если placeholder или другой locator изменится, исправление выполняется в одном классе, а не во всех тестах. Это снижает дублирование и стоимость поддержки автотестов.

В реальном проекте аналогично создаются:

- `LoginPage` для входа пользователя;
- `CartPage` для работы с корзиной;
- `CheckoutPage` для оформления заказа;
- компонент `Header` для общего меню и профиля.

Например, тест не должен повторять заполнение email и пароля в каждом сценарии:

```python
login_page.login("qa@example.com", "password")
expect(home_page.profile_menu).to_be_visible()
```

## Граница ответственности

Page Object отвечает за взаимодействие со страницей: найти элемент, ввести данные, нажать кнопку, вернуть locator для проверки.

Тест отвечает за сценарий и ожидаемый результат. Поэтому assertions обычно остаются в тесте. Так тест показывает, что проверяется, а Page Object скрывает, как именно приложение используется.

Не следует складывать в один класс всю систему. Слишком большой класс превращается в `God Object`, который трудно менять и переиспользовать. Лучше выделять страницы и крупные компоненты отдельно.

## Связь с fixture

Fixture отвечает за жизненный цикл и подготовку:

```text
page + base_url -> todo_page fixture -> TodoPage -> test
```

Page Object отвечает за API взаимодействия со страницей. Fixture отвечает за создание и передачу этого объекта тесту. Это разные уровни ответственности.

## Важное замечание по типам

Тип `TodoPage` в сигнатуре теста документирует, что тест получает объект страницы, а не обычный `Page`. Тип `Locator` показывает, что методы `todo_title()` и `items_left()` возвращают объект для последующей проверки через `expect`.

## Правило дня

Локаторы и действия страницы скрываем в Page Object, а пользовательский сценарий и проверки оставляем в тесте.
