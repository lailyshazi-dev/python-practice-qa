# День 68: `pytest.param` и негативные UI-кейсы

## Цель урока

Научиться связывать входные данные, ожидаемый результат и понятное имя кейса внутри одного параметризованного набора.

## Что сделано

- Добавлен параметризованный тест результата добавления задачи.
- Использован `pytest.param`.
- Для валидного и пустого названия заданы разные ожидаемые количества задач.
- Добавлены читаемые идентификаторы `valid-title` и `empty-title`.
- Проверен позитивный и негативный UI-сценарий.

## `pytest.param`

```python
@pytest.mark.parametrize(
    "title, expected_count",
    [
        pytest.param(
            "Buy milk",
            1,
            id="valid-title",
        ),
        pytest.param(
            "",
            0,
            id="empty-title",
        ),
    ],
)
def test_add_todo_result(
    todo_page: TodoPage,
    title: str,
    expected_count: int,
):
    todo_page.add_todo(title)
    expect(todo_page.todo_items).to_have_count(
        expected_count
    )
```

`pytest.param` хранит всё, что относится к одному варианту: входные данные, ожидаемый результат, `id` и при необходимости mark.

Тест запускается как два отдельных кейса:

```text
test_add_todo_result[valid-title]
test_add_todo_result[empty-title]
```

## Позитивный и негативный сценарий

Позитивный кейс проверяет, что корректное название создаёт задачу. Негативный кейс проверяет, что пустое название не создаёт запись.

Такой подход особенно полезен для форм. Один параметризованный набор может содержать валидный email, пустой email, неправильный формат и слишком длинное значение вместе с ожидаемым сообщением ошибки.

## Реальные примеры

### Права пользователей

```python
pytest.param(
    "viewer",
    False,
    id="read-only",
)
```

Параметр может содержать роль и ожидаемое наличие кнопки удаления.

### Интернет-магазин

Для товара можно передавать название, ожидаемую цену и категорию. Один сценарий проверяет карточки Keyboard, Mouse и Monitor.

### API

Для API `pytest.param` удобно использовать для status code, payload и ожидаемого сообщения ошибки. Каждый набор данных становится отдельным понятным кейсом в отчёте.

## `ids` и отчёты

Плохое имя:

```text
test_add_todo_result[-]
```

Хорошее имя:

```text
test_add_todo_result[empty-title]
```

В CI и HTML-отчёте сразу видно, какой бизнес-вариант сломался.

## Marks внутри параметров

В более сложных наборах отдельный параметр можно пометить:

```python
pytest.param(
    "old-browser-case",
    marks=pytest.mark.xfail,
    id="known-issue",
)
```

Использовать это нужно осознанно и только для подтверждённого дефекта или известного ограничения, а не для сокрытия нестабильности.

## Ограничения

Параметризация подходит, когда структура сценария одинакова. Если для разных вариантов нужны разные шаги и разные проверки, лучше создать отдельные тесты.

Слишком большое количество параметров увеличивает время запуска. Поэтому данные иногда выносят в отдельный модуль или делят на тематические наборы.
