## Зачем подменять внешний API

Тест нашего клиента не должен падать только потому, что внешний сервер недоступен, интернет работает медленно или исчерпан лимит запросов. Поэтому настоящий сетевой метод временно заменяется контролируемой функцией.

```python
def fake_get(url, params, timeout):
    captured_request.update(
        {
            "url": url,
            "params": params,
            "timeout": timeout,
        }
    )
    return expected_response


monkeypatch.setattr(api_client.session, "get", fake_get)
```

На время одного теста вызов:

```python
api_client.session.get(...)
```

попадает в `fake_get()`. После теста `monkeypatch` автоматически возвращает настоящий метод.

## Первый тест: граница с библиотекой requests

```python
response = api_client.get(
    "/posts",
    params={"userId": 1},
)
```

Тест проверяет, что `ApiClient` передал в Session:

```text
url     = https://.../posts
params  = {"userId": 1}
timeout = настройка клиента
```

Это проверка контракта между нашим кодом и `requests.Session`.

## Почему используется `object()`

```python
expected_response = object()
```

Для этого теста не нужны настоящий status code, JSON и headers. Нужен только уникальный объект, который вернёт fake-функция.

```python
assert response is expected_response
```

Оператор `is` подтверждает, что клиент вернул именно тот же объект, а не копию или другое значение.

## Второй тест: вспомогательный метод

```python
monkeypatch.setattr(api_client, "get", fake_get)

response = api_client.get_post(7)
```

Здесь подменяется уже наш метод `ApiClient.get()`. Проверка подтверждает, что:

```python
get_post(7)
```

вызывает:

```python
get("/posts/7")
```

Так тесты разделяют ответственность:

- один проверяет отправку данных в `requests`;
- второй проверяет построение endpoint.

## Test double

`Test double` — общее название объекта или функции, заменяющей настоящую зависимость в тесте.

В этом уроке `fake_get()`:

- принимает те же нужные аргументы;
- сохраняет их для проверки;
- не выполняет HTTP-запрос;
- возвращает заранее подготовленный результат.

Позже мы отдельно разберём mock, stub, fake и spy. На практике названия иногда смешивают, поэтому важнее понимать поведение замены.

## Unit и integration тесты

Unit-тест с подменой:

- проверяет только наш код;
- быстрый;
- повторяемый;
- работает без интернета;
- не доказывает, что настоящий сервер доступен.

Integration-тест с реальным JSONPlaceholder:

- проверяет совместную работу клиента, сети и сервера;
- обнаруживает изменение реального API;
- медленнее;
- может упасть из-за внешней проблемы.

Оба уровня нужны. Unit-тесты дают быструю диагностику нашей логики, integration-тесты подтверждают реальное взаимодействие.

## Где это нужно в реальной работе

- Платёжный API нельзя вызывать настоящей оплатой в каждом unit-тесте.
- Сервис отправки SMS или email может иметь плату и лимиты.
- API партнёра может быть недоступно на локальной машине.
- Нужный ответ `500` или timeout трудно стабильно дождаться от настоящего сервера.
- CI должен быстро проверять код даже при проблемах внешней сети.
- Редкий сценарий можно воспроизвести заранее подготовленным response.

Например, тест checkout подменяет платёжный сервис и заставляет его вернуть отказ. Это позволяет проверить, что заказ не отмечается оплаченным, даже не обращаясь к настоящему банку.

## Новые слова

- `test double` — замена настоящей зависимости в тесте.
- `fake function` — управляемая функция вместо настоящей.
- `captured arguments` — сохранённые аргументы вызова.
- `unit test` — изолированная проверка небольшой части кода.
- `integration test` — проверка совместной работы нескольких компонентов.
- `dependency` — внешний объект или сервис, от которого зависит код.

## Правило дня

Unit-тест проверяет нашу логику под контролем, а integration-тест подтверждает реальное взаимодействие.
