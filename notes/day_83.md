# День 83: первый Selenium-тест, WebDriver fixture

## Цель урока

Добавить в проект Selenium: отдельную папку тестов, фикстуру WebDriver с корректным запуском и завершением браузера, первый UI-тест с явными ожиданиями.

## Структура

Selenium-тесты живут отдельно от Playwright:

```text
tests/
  selenium/
    conftest.py
    test_todo_page.py
  ui/            # Playwright
```

Разделение нужно, потому что у инструментов разные фикстуры и разный способ управления браузером. Общая настройка `base_url` при этом переиспользуется: обе группы тестов ходят на один и тот же TodoMVC.

## Фикстура WebDriver

```python
@pytest.fixture
def selenium_driver():
    options = webdriver.ChromeOptions()

    if os.getenv("CI"):
        options.add_argument("--headless=new")

    driver = webdriver.Chrome(options=options)
    driver.set_window_size(1440, 900)

    yield driver

    driver.quit()
```

Разбор по частям:

- `ChromeOptions` — контейнер настроек запуска браузера.
- `--headless=new` включается только в CI: локально удобно видеть браузер, на сервере экрана нет.
- `set_window_size` фиксирует размер окна, чтобы вёрстка и селекторы вели себя одинаково на любой машине.
- Всё до `yield` — setup, всё после — teardown.

## Почему --headless=new, а не --headless

Исторически у Chrome было две реализации headless-режима. Старый `--headless` — отдельная урезанная сборка (headless shell): часть функций отсутствовала, рендеринг и поведение местами отличались от настоящего браузера. Тест мог проходить в headless и падать в обычном режиме или наоборот.

`--headless=new` (Chrome 109+) — это тот же самый Chrome без окна: то же поведение, что видит пользователь. В автотестах используется только новый режим.

## Кто вызывает driver.quit() при упавшем тесте

`assert` бросает `AssertionError`. pytest ловит исключение, помечает тест упавшим и затем выполняет teardown всех фикстур — код после `yield`. Поэтому браузер закрывается независимо от результата теста.

Тонкость: если исключение произошло в фикстуре до `yield` (например, браузер не смог запуститься), teardown не выполняется — но в этот момент закрывать ещё нечего.

## Явные ожидания

В Selenium нет автоожиданий: `find_element` ищет элемент немедленно, и если элемента ещё нет в DOM, сразу получаем `NoSuchElementException`. Поэтому перед действием элемент нужно дождаться явно:

```python
todo_input = WebDriverWait(selenium_driver, 10).until(
    EC.visibility_of_element_located((By.CLASS_NAME, "new-todo"))
)
```

- `WebDriverWait(driver, 10)` — опрашивать условие до 10 секунд.
- `expected_conditions` (EC) — библиотека готовых условий: элемент видим, кликабелен, присутствует в DOM.
- `time.sleep(N)` — плохая замена: фиксированная пауза либо слишком короткая (тест мигает), либо слишком длинная (тест медленный). WebDriverWait продолжает работу сразу, как условие выполнилось.

## Главное сравнение: Selenium vs Playwright

Перед `page.click()` Playwright сам выполняет actionability-проверки: элемент прикреплён к DOM, видим, стабилен (не движется из-за анимации), активен (не disabled), не перекрыт другим элементом. Ожидания встроены в каждое действие.

В Selenium этих проверок нет — то же самое пишется вручную через `WebDriverWait` + `expected_conditions`. Это не про ожидание ответа сервера: и там и там речь о состоянии элемента на странице.

Формулировка для собеседования: Playwright ждёт готовность элемента автоматически при каждом действии, в Selenium готовность элемента проверяет инженер явными ожиданиями.

## Маркеры

Тест помечен маркером категории:

```python
@pytest.mark.selenium
```

Маркер `selenium` зарегистрирован в `pytest.ini`. Запуск только Selenium-тестов:

```text
pytest -m selenium
```

Вывод `1 passed, 111 deselected` означает: pytest собрал все 112 тестов проекта, но по фильтру `-m selenium` выполнил один, остальные 111 отсеял (deselected — отфильтрован маркером, а не skipped).

## Урок про окружение

Активация `.venv` действует только внутри одного сеанса терминала. Новое окно — снова системный Python и ошибка `No module named pytest`. Активация в PowerShell:

```text
.venv\Scripts\Activate.ps1
```

Проверка, какой Python активен:

```text
Get-Command python | Select-Object Source
```

Тот же принцип в CI: каждый запуск начинается с чистого окружения и настраивается явно.

## Утечка новой категории тестов в CI

Регрессионная джоба отбирала тесты через отрицание:

```yaml
python -m pytest -m "not smoke and not ui"
```

Новый Selenium-тест помечен только маркером `selenium`, поэтому под это условие он подошёл и попал в регрессию, хотя туда его никто не добавлял. Джоба прошла успешно, но результат был случайным: тест выжил только потому, что на `ubuntu-latest` предустановлен Chrome, а `--headless=new` включился по переменной `CI`.

Цена утечки видна по времени шага:

```text
до:    95 passed, 16 deselected in 1.66s
после: 96 passed, 16 deselected in 25.87s
```

Регрессионная джоба задумана как быстрая проверка без браузеров: у неё нет шага установки браузера, в отличие от smoke и UI-джоб. Один браузерный тест сделал её в пятнадцать раз медленнее.

Исправление — явное исключение категории:

```yaml
python -m pytest -m "not smoke and not ui and not selenium" ```

После правки регрессия вернулась к прежнему виду: `95 passed, 17 deselected`, шаг снова около полутора секунд. Сумма `passed + deselected` осталась равной 112 — все тесты проекта учтены.

Правило: отбор тестов через отрицание молча поглощает каждую новую категорию маркеров. Такое выражение требует ревизии при добавлении любого нового вида тестов. Более устойчивый вариант — положительный отбор нужных маркеров.

## Как читать прогон CI

Первый запуск после урока показал:

```text
95 passed, 16 deselected in 1.66s
```

Числа выглядели правдоподобно, но проверка не состоялась: это был запуск `workflow_dispatch` на ветке `master`, то есть на коде до нового коммита. Две улики указывали на это сразу:

- сумма `95 + 16 = 111`, а в ветке уже 112 тестов;
- время 1.66s — браузерный тест столько не выполняется, только запуск Chrome занимает секунды.

Порядок чтения прогона: сначала событие (`push`, `pull_request`, `workflow_dispatch`) и коммит, затем цифры. Push feature-ветки сам по себе pipeline не запускает, если в триггерах указан только `push: [master]` — прогон на изменениях появляется после открытия Pull Request.

Дополнительно: время джобы определяется не количеством тестов, а тем, поднимает ли она тяжёлые ресурсы. 95 небраузерных тестов дешевле одного браузерного.

## Правило дня

Selenium делает ожидания обязанностью инженера: каждое действие с элементом начинается с явного ответа на вопрос «чего именно я жду».

Второе правило дня: зелёный CI не доказывает, что тест запустился там, где задумано. Проверять нужно событие, коммит и состав прогона.
