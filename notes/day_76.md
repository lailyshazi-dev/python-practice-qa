# День 76: smoke-набор перед полной регрессией в CI

## Цель урока

Выделить критические тесты маркером `smoke` и запускать их в GitHub Actions раньше полного набора.

## Smoke и regression

Smoke-тесты быстро отвечают на вопрос: работает ли основная функциональность настолько, чтобы продолжать проверку системы.

Regression-тесты проверяют более широкий набор функций и помогают найти дефекты, появившиеся после изменений.

Примеры smoke-проверок:

- приложение открывается;
- основной документ возвращает HTTP `200`;
- пользователь может выполнить ключевое действие;
- критическая функция возвращает ожидаемый результат.

Примеры регрессионных проверок:

- позитивные, негативные и граничные сценарии;
- фильтрация и изменение данных;
- обработка ошибок сервера;
- разные комбинации входных параметров.

## Маркировка тестов

В проекте уже были зарегистрированы маркеры в `pytest.ini`:

```ini
markers =
    smoke: critical fast tests
    regression: full regression test set
```

К smoke-набору добавлены две UI-проверки:

```python
@pytest.mark.smoke
def test_todomvc_initial_document_returns_ok(...):
    ...
```

```python
@pytest.mark.smoke
def test_user_can_add_todo(...):
    ...
```

Параметризованный тест добавления задачи создаёт два отдельных тестовых случая. Поэтому один декоратор `smoke` помечает оба случая.

Маркер выбирает тесты независимо от их расположения. Один smoke-набор может содержать calculator-, API- и UI-тесты из разных файлов.

## Запуск по маркеру

```powershell
.\.venv\Scripts\python.exe -m pytest -m smoke -v
```

Ключ `-m smoke` означает: выполнить только тесты с маркером `smoke`. Остальные тесты не считаются пропущенными или упавшими — pytest показывает их как `deselected`.

## Smoke-шаг в GitHub Actions

Перед полной регрессией добавлен отдельный шаг:

```yaml
      - name: Run smoke tests
        run: |
          python -m pytest -m smoke \
            --html=reports/smoke-report.html \
            --self-contained-html \
            --junitxml=reports/smoke-junit.xml
```

Следующий шаг запускает весь тестовый набор:

```yaml
      - name: Run full test suite
        run: |
          python -m pytest \
            --html=reports/report.html \
            --self-contained-html \
            --junitxml=reports/junit.xml
```

По умолчанию GitHub Actions выполняет шаги последовательно. Если smoke-шаг падает, следующий обычный шаг полной регрессии не запускается. Шаг загрузки артефактов всё равно выполняется благодаря условию `if: ${{ !cancelled() }}`.

## Отдельные отчёты

Smoke и полный набор сохраняют разные файлы:

```text
reports/smoke-report.html
reports/smoke-junit.xml
reports/report.html
reports/junit.xml
```

Разные имена нужны, чтобы второй запуск не перезаписал результаты первого.

## Ошибка с YAML-отступами

Первоначально шаг `Run smoke tests` был сдвинут на два лишних пробела и оказался вложен в предыдущий шаг. Локальный pytest не обнаруживает такие ошибки, потому что он проверяет тесты, а не синтаксис GitHub Actions.

Все элементы списка внутри `steps` должны иметь одинаковый отступ:

```yaml
steps:
  - name: First step
  - name: Second step
```

После исправления был создан отдельный коммит, ветка объединена с `master`, а workflow успешно прошёл.

## Реальные примеры применения

### Проверка Pull Request

Перед полной регрессией запускаются несколько критических тестов. Если приложение не открывается или невозможно выполнить основное действие, команда быстро получает результат и не тратит время runner на длинный набор.

### Проверка после deployment

После выкладки smoke-набор проверяет доступность сервиса, авторизацию и ключевую бизнес-операцию. Это не полная проверка продукта, а быстрый сигнал о работоспособности версии.

### Ночная регрессия

Полный набор может запускаться ночью по расписанию. Он содержит больше позитивных, негативных и интеграционных сценариев, поэтому выполняется дольше.

## Правило дня

Smoke-набор должен быть небольшим, быстрым и проверять действительно критические пользовательские пути. Если пометить как smoke почти все тесты, он потеряет смысл быстрого сигнала.
