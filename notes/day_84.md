# День 84: expected_conditions, сообщения в ожиданиях, flaky-тесты

## Цель урока

Освоить набор явных ожиданий Selenium, научиться выбирать условие под задачу и диагностировать падения по таймауту.

## Каталог expected_conditions

| Условие | Что проверяет | Когда применять |
|---|---|---|
| `presence_of_element_located` | элемент есть в DOM | элемент невидим стилями, но существует |
| `visibility_of_element_located` | есть в DOM и видим | обычное ожидание перед чтением |
| `element_to_be_clickable` | видим и активен | перед кликом по обычной кнопке |
| `text_to_be_present_in_element` | в элементе появился текст | счётчики, статусы, уведомления |
| `invisibility_of_element_located` | элемент исчез или скрыт | проверка удаления |
| `staleness_of` | элемент отвалился от DOM | страница перерисовалась |

Условия различаются и по возвращаемому значению:

```python
EC.visibility_of_element_located(TODO_INPUT)                 # вернёт WebElement
EC.text_to_be_present_in_element(TODO_COUNT, "1 item left")  # вернёт True/False
```

Первое принимает один аргумент (локатор) и отдаёт элемент, поэтому результат присваивают переменной. Второе принимает локатор и ожидаемый текст, отдаёт булево — его вызывают ради самого ожидания.

## Фикстура wait и константы-локаторы

Повторяющийся `WebDriverWait(driver, 10)` вынесен в фикстуру:

```python
EXPLICIT_TIMEOUT = 10


@pytest.fixture
def wait(selenium_driver):
    return WebDriverWait(selenium_driver, EXPLICIT_TIMEOUT)
```

Фикстура зависит от другой фикстуры — pytest сам выстраивает порядок создания. Таймаут задан в одном месте, менять его для медленного CI нужно будет однажды.

Локаторы вынесены в константы модуля:

```python
TODO_INPUT = (By.CLASS_NAME, "new-todo")
TODO_ITEM = (By.CSS_SELECTOR, ".todo-list li")
```

Локатор в Selenium — кортеж из способа поиска и значения. Отсюда двойные скобки в вызовах: внешние принадлежат функции, внутренние кортежу.

## Константы и глобальные переменные

Предупреждение «не используй глобальные переменные» относится к изменяемому разделяемому состоянию, а не к любому имени на уровне модуля.

Опасный вариант:

```python
driver = webdriver.Chrome()   # состояние на уровне модуля
```

Такой браузер общий для всех тестов: остатки данных от предыдущего теста ломают следующий, порядок запуска начинает влиять на результат, никто не закрывает процесс, параллельный запуск невозможен. Именно от этого спасают фикстуры: у состояния появляется владелец и жизненный цикл.

Безопасный вариант:

```python
EXPLICIT_TIMEOUT = 10
TODO_INPUT = (By.CLASS_NAME, "new-todo")
```

Значения только читаются, типы неизменяемые (число, кортеж), имена в верхнем регистре по PEP 8. Кортеж изменить физически нельзя, в отличие от списка или словаря — поэтому «константа» со словарём внутри защиты не даёт.

Правило: состояние с жизненным циклом — в фикстуры, неизменяемые значения — в константы, зависящее от окружения — в конфиг.

## Разбор реального падения: opacity 0

Тест отметки задачи выполненной сначала использовал очевидное условие:

```python
toggle = wait.until(EC.element_to_be_clickable(TODO_TOGGLE))
```

Результат:

```text
TimeoutException  на строке клика по чекбоксу
1 failed, 1 passed in 32.50s
```

`TimeoutException` сообщает только «не дождался». Чтобы понять причину, элемент был опрошен напрямую:

```text
tag: input        enabled: True
displayed: False  size: {'height': 40, 'width': 40}
opacity: 0        visibility: visible   display: block
```

Чекбокс в TodoMVC занимает свои 40x40 пикселей и принимает клики, но у него `opacity: 0`: галочку рисует CSS-фон, сам `input` прозрачный. Selenium считает элемент с нулевой прозрачностью неотображаемым, `is_displayed()` возвращает `False`. Условие `element_to_be_clickable` требует видимости, поэтому не выполнится никогда.

Вывод: `is_displayed()` и «пользователь может кликнуть» — разные вещи. Клик WebDriver проверяет попадание указателя в элемент, прозрачность ему не мешает.

Решение — ослабить условие до присутствия в DOM и объяснить причину комментарием:

```python
# .toggle has opacity: 0, so is_displayed() is False and
# element_to_be_clickable never succeeds. Wait for presence instead:
# transparency does not block a WebDriver click.
toggle = wait.until(EC.presence_of_element_located(TODO_TOGGLE))
toggle.click()
```

Чего делать не следовало: ставить `time.sleep`, увеличивать таймаут, кликать через `execute_script`. Ожидание было не тем, а не коротким.

## Методика разбора TimeoutException

1. Определить, на какой строке сработал таймаут.
2. Открыть страницу и опросить элемент: `is_displayed`, `is_enabled`, `size`, вычисленные стили.
3. Сравнить фактическое состояние с требованиями выбранного условия.
4. Заменить условие на соответствующее реальности либо признать падение багом продукта.

## Сообщения в ожиданиях

У `until()` есть второй параметр — текст для исключения:

```python
wait.until(
    EC.text_to_be_present_in_element(TODO_COUNT, "1 item left"),
    "Counter did not show '1 item left' after adding a todo",
)
```

Без него падение выглядит так:

```text
E  selenium.common.exceptions.TimeoutException: Message:
```

Пустое сообщение означает: тест десять секунд ждал неизвестно чего. С сообщением причина видна сразу из отчёта CI, без чтения кода.

Сообщения пишутся на английском. Кириллица в выводе pytest на Windows превращается в escape-последовательности вида `Сч`, потому что консоль не может отобразить символы. Selenium текст не портит — это ограничение кодировки терминала, но диагностика, читаемая не везде, свою задачу не выполняет.

## Проверка отсутствия элемента

```python
wait.until(EC.invisibility_of_element_located(TODO_ITEM), "Todo is still visible")

assert selenium_driver.find_elements(*TODO_ITEM) == []
```

`wait.until` синхронизирует, `assert` фиксирует факт. Оборачивать `wait.until` в `assert` бессмысленно: ожидание само проваливает тест исключением, а при успехе возвращает истину — такой `assert` не проверяет ничего.

Разница методов поиска:

- `find_element` — бросает `NoSuchElementException`, если не нашёл;
- `find_elements` — возвращает пустой список.

Для проверки отсутствия годится только второй. Звёздочка в `find_elements(*TODO_ITEM)` распаковывает кортеж в два аргумента.

## implicitly_wait

Второй механизм ожиданий: `driver.implicitly_wait(10)` заставляет каждый `find_element` ждать появления элемента в DOM.

Не используется в проекте, потому что:

- умеет ждать только присутствие, но не видимость, кликабельность или текст;
- применяется глобально ко всем поискам, включая проверки отсутствия, которые из-за него замедляются;
- при смешивании с `WebDriverWait` таймауты складываются непредсказуемо, о чём предупреждает документация Selenium.

Правило: в проекте только явные ожидания.

## Нестабильные (flaky) тесты

Flaky-тест то падает, то проходит без изменений кода. Как отличить плохое ожидание от бага продукта:

- падает в одном и том же месте, чаще в CI и под нагрузкой — ожидание;
- падает с `TimeoutException` — ждали не того или не дождались;
- падает со стабильным несовпадением значений — баг продукта;
- десять прогонов, упал три — flaky; упал десять из десяти — баг.

Лечение `time.sleep` и автоматическим перезапуском прячет симптом, а не устраняет причину.

## Функция вместо фикстуры

Шаг `add_todo` оформлен обычной функцией. Фикстура может принимать параметры через приём «фикстура-фабрика», то есть технически это было возможно. Причина в разделении ролей:

- фикстура готовит и убирает состояние, выполняется до и после теста;
- `add_todo` — действие пользователя, шаг сценария внутри теста.

Спрятав шаг сценария в фикстуру, тест перестаёт читаться как история: открыл, добавил, отметил, очистил, проверил.

## Уровни тестирования (повторение к собеседованию)

| | Smoke | Sanity | Regression |
|---|---|---|---|
| Вопрос | Работает ли сборка вообще? | Починили ли конкретную вещь? | Не сломали ли работавшее? |
| Охват | широкий, поверхностный | узкий, глубокий | широкий и глубокий |
| Когда | сразу после сборки | после багфикса | после изменений, перед релизом |

В проекте smoke и regression разделены маркерами и отдельными джобами, причём регрессия объявлена через `needs: smoke` и не запускается, пока smoke не прошёл. Это и есть принцип «нет смысла тестировать дальше, если сборка не дышит». Роль sanity выполняет точечный прогон через `-k` или маркер после исправления.

## Правило дня

Ожидание отвечает на вопрос «чего именно я жду», а сообщение к нему — на вопрос «что пойму, когда не дождусь». Без второго ответа падение теста превращается в расследование.
