# День 67: Параметризация UI-тестов

## Цель урока

Запустить один и тот же UI-сценарий с несколькими наборами данных, не копируя тело теста.

## Что сделано

- Тест `test_user_can_add_todo` сделан параметризованным.
- Добавлены два значения `title`.
- Для запусков заданы читаемые идентификаторы `locators` и `assertions`.
- Один сценарий теперь создаёт два независимых тестовых кейса.

## Параметризация

```python
@pytest.mark.parametrize(
    "title",
    [
        "Learn Playwright locators",
        "Practice UI assertions",
    ],
    ids=[
        "locators",
        "assertions",
    ],
)
def test_user_can_add_todo(
    todo_page: TodoPage,
    title: str,
):
    todo_page.add_todo(title)
    expect(todo_page.todo_title(title)).to_be_visible()
```

pytest подставляет каждое значение и запускает тест отдельно:

```text
test_user_can_add_todo[locators]
test_user_can_add_todo[assertions]
```

Каждый запуск получает отдельную fixture `todo_page`, поэтому состояние не переносится между вариантами.

## Зачем нужны `ids`

Без `ids` pytest обычно показывает значения параметров в имени теста. `ids` делают отчёт понятнее, особенно если параметры длинные или содержат payload.

В HTML-отчёте и CI проще сразу понять, какой вариант упал:

```text
test_user_can_add_todo[assertions] FAILED
```

## Реальные примеры

### Группы пользователей

Один сценарий можно запустить для ролей:

```python
@pytest.mark.parametrize(
    "role",
    ["admin", "manager", "viewer"],
)
def test_user_sees_dashboard(todo_page, role):
    ...
```

Далее проверяется, что у администратора есть кнопка удаления, у менеджера есть редактирование, а viewer имеет только просмотр.

### Товары на витрине

Параметрами могут быть названия, цены или категории товаров:

```python
@pytest.mark.parametrize(
    "product",
    ["Keyboard", "Mouse", "Monitor"],
)
def test_product_can_be_added_to_cart(product):
    ...
```

### Формы

Параметризация подходит для валидных и невалидных данных: email, телефон, пароль, страна или способ оплаты.

### API

Этот же принцип уже применялся в проекте для проверки нескольких post id. UI и API используют одинаковую идею: общий сценарий плюс набор входных данных.

## Плюсы и ограничения

Преимущества:

- меньше дублирования;
- одинаковая логика проверки;
- понятные отчёты;
- проще добавлять новые варианты.

Ограничение: если сценарии начинают сильно отличаться, не нужно искусственно объединять их параметризацией. В таком случае лучше создать разные тесты.

Параметризация не заменяет fixture. Параметр описывает входные данные, а fixture подготавливает окружение и зависимости.
