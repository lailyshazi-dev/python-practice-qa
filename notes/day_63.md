## Пользовательский сценарий

Сегодня тест впервые не только прочитал страницу, но и изменил её состояние:

```text
Открыть TodoMVC
→ найти поле
→ ввести задачу
→ нажать Enter
→ проверить созданную задачу
```

Это простой end-to-end пользовательский путь внутри web-приложения.

## Ввод текста

```python
todo_input = page.get_by_placeholder(
    "What needs to be done?"
)

todo_input.fill("Learn Playwright locators")
todo_input.press("Enter")
```

- `get_by_placeholder()` находит поле по пользовательской подсказке.
- `fill()` заменяет текущее содержимое поля.
- `press("Enter")` отправляет клавиатурное событие.

`fill()` отличается от посимвольного `type()`: он быстро устанавливает полное значение. Посимвольный ввод нужен только там, где приложение действительно зависит от отдельных keyboard events.

## Проверка результата

```python
expect(
    page.get_by_text(
        "Learn Playwright locators",
        exact=True,
    )
).to_be_visible()
```

`exact=True` требует точного текстового совпадения. Без него locator может найти более длинную строку, содержащую искомый текст.

Дополнительные проверки:

```python
expect(page.get_by_test_id("todo-item")).to_have_count(1)
expect(page.get_by_text("1 item left", exact=True)).to_be_visible()
```

Один сценарий проверяет не только появление текста, но и количество элементов и связанный счётчик.

## Test ID

```python
page.get_by_test_id("todo-item")
```

Test ID — специальный стабильный контракт между приложением и автотестами. Он полезен, когда у элемента нет подходящей роли, label или уникального пользовательского текста.

Приоритет locator обычно такой:

1. Role и accessible name для интерактивных элементов.
2. Label для полей формы.
3. Пользовательский текст для неинтерактивного содержимого.
4. Явный test ID.
5. Короткий устойчивый CSS, если других вариантов нет.

Не следует начинать с длинного XPath, зависящего от всей DOM-структуры.

## Checkbox

```python
toggle = page.get_by_role(
    "checkbox",
    name="Toggle Todo",
)
toggle.check()

expect(toggle).to_be_checked()
```

`check()` выражает цель лучше обычного `click()`: после операции checkbox должен быть отмечен. Если он уже отмечен, Playwright не переключит его обратно.

Это делает действие более идемпотентным и понятным.

## Web-first assertions

```python
expect(toggle).to_be_checked()
expect(locator).to_have_count(1)
expect(locator).to_be_visible()
```

Playwright повторяет проверку до успеха или timeout. Это важно для динамического UI, где DOM изменяется не мгновенно.

Не нужно вставлять `sleep` между каждым действием и проверкой.

## Изоляция browser context

```python
def test_new_browser_context_has_empty_todo_list(page: Page):
    page.goto(TODO_URL)

    expect(page.get_by_test_id("todo-item")).to_have_count(0)
```

TodoMVC хранит состояние в браузере. Однако pytest-playwright создаёт отдельный browser context для каждого теста, поэтому cookies и local storage предыдущего теста не протекают в следующий.

Изолированный тест:

- не зависит от порядка запуска;
- не использует данные другого теста;
- может запускаться отдельно;
- легче диагностируется;
- безопаснее выполняется параллельно.

## Где это нужно в реальной работе

- Каждый login-тест получает чистую сессию.
- Корзина одного пользователя не попадает в тест другого.
- Cookies эксперимента не изменяют следующий сценарий.
- Local storage старой версии приложения не ломает новый тест.
- Параллельные тесты не делят один browser context.

Например, один тест проверяет администратора, другой обычного пользователя. Если использовать общий context, второй тест может случайно сохранить административную авторизацию и дать ложный положительный результат.

## Новые слова

- `user action` — действие пользователя в интерфейсе.
- `placeholder` — подсказка внутри пустого поля.
- `test ID` — специальный идентификатор для автотеста.
- `browser context` — изолированная браузерная сессия.
- `local storage` — хранилище данных сайта в браузере.
- `exact match` — точное совпадение.
- `idempotent action` — повторное действие сохраняет ожидаемое состояние.

## Правило дня

Каждый UI-тест сам создаёт своё состояние и не зависит от результатов других тестов.
